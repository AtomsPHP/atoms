## `atoms.json`

The `atoms.json` file is generated by `vendor/bin/atoms init`. It describes where your Atom code lives and the environments you deploy to.

```json title="atoms.json"
{
    "project": "my-app",
    "paths": {
        "atoms": "app/Atoms",
        "shared": "app/Atoms/Shared"
    },
    "environments": {
        "production": {
            "worker_name": "my-app",
            "account_id": "",
            "debug_endpoints": false,
            "callback_url": "https://example.com/atoms/callback",
            "custom_domains": ["atoms.example.com"]
        },
        "staging": {
            "worker_name": "my-app-staging",
            "account_id": "",
            "debug_endpoints": true,
            "callback_url": "https://staging.example.com/atoms/callback"
        }
    }
}
```

| Key | Required | Default |
|---|---|---|
| `project`<br>Project slug, recorded in the build manifest | yes | — |
| `paths.atoms`<br>Directory holding your Atom classes | yes | — |
| `paths.shared`<br>Directory of shared code, such as DTOs, used on both the Atom side and the App side | no | `<paths.atoms>/Shared` |
| `environments.<name>.worker_name`<br>Name of the Cloudflare Worker this environment deploys to | yes | — |
| `environments.<name>.account_id`<br>Cloudflare account that owns the Worker | no | — |
| `environments.<name>.callback_url`<br>URL where the Worker reaches your app for `app()` and `dispatch()` | no | — |
| `environments.<name>.debug_endpoints`<br>Whether the Worker exposes its `/debug` routes | no | `false` |
| `environments.<name>.custom_domains`<br>[Hostnames the Worker answers on](/guides/environments/#custom-domains) | no | `[]` |

`account_id` is needed only when your Cloudflare credentials can reach more
than one account. `callback_url` must use HTTPS, except for local development,
where an HTTP URL on `localhost`, `127.0.0.1` or `[::1]` works too.

## Environment variables

You can also set the Cloudflare API token, `account_id` and `callback_url`
with the environment variables `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`
and `ATOMS_CALLBACK_URL`. In CI, set them as job variables, taking the API
token from your secret store. A variable overrides the matching key in
`atoms.json`; [Environments](/guides/environments/#where-values-come-from)
lists the full order.

### `.env.atoms.<environment>`

When you deploy or run `atoms dev` from your own machine, you can keep these
variables in a file beside `atoms.json` named after the environment:

```bash
# .env.atoms.production
CLOUDFLARE_API_TOKEN=…
ATOMS_CALLBACK_URL=https://my-tunnel.example.com/atoms/callback
```

The file is optional, and `atoms init` adds `/.env.atoms.*` to your
`.gitignore`. Write one `KEY=value` per line, with optional quotes and `#`
comments. A command reads only the file for the environment you pass to
`--env`, and a variable set in your shell takes priority over it.

## `atoms-worker/wrangler.jsonc`

Unlike `atoms.json` and `atoms-composer.json`, this JSONC file permits comments.

The [Worker scaffold command](/getting-started/install/#initialize-the-project)
printed by `atoms init` creates `atoms-worker/`, including this Wrangler
configuration file. It's yours to edit: add logging,
placement, limits and runtime vars at the top level, and they apply to every
environment. Keep the keys marked `RUNTIME-REQUIRED`, which the Worker needs in
order to load.

Settings that differ between environments go in `atoms.json`. `atoms deploy`
and `atoms dev` combine the two using Wrangler's [generated
configuration](https://developers.cloudflare.com/workers/wrangler/configuration/#generated-wrangler-configuration)
feature. They write a copy of this file with the selected environment's Worker
name, custom domains, callback URL and debug setting filled in, to
`atoms-worker/.wrangler/deploy/wrangler.json`, alongside a `config.json` that
tells Wrangler to use the copy. Wrangler prints "Using redirected Wrangler
configuration" when it does. Atoms removes both files after Wrangler returns
normally, including when Wrangler reports an error. Abrupt termination of the
parent Atoms process can prevent that cleanup.

Define environments in `atoms.json` rather than in Wrangler's `env.<name>`
sections, and declare hostnames under `custom_domains` rather than as routes
here. The generated copy leaves out both, and `atoms deploy` prints a notice
when it finds routes in this file.

### Recover a stale Wrangler redirect

A leftover redirect can make a later direct Wrangler invocation use a previously
selected environment. Before changing generated files, stop this project's Atoms
and Wrangler processes and confirm they have exited. A closed terminal alone is
not proof that every child process stopped.

From the application root, inspect the redirect and the generated Worker name:

```bash
cat atoms-worker/.wrangler/deploy/config.json
node -e 'const fs = require("node:fs"); const c = JSON.parse(fs.readFileSync("atoms-worker/.wrangler/deploy/wrangler.json", "utf8")); console.log(c.name);'
```

Confirm that `configPath` is `wrangler.json` and that the Worker name matches the
stale environment in this project's `atoms.json`. Check the generated file
against `atoms-worker/wrangler.jsonc` before proceeding. The redirect format alone
does not establish that Atoms owns it. Do not move another tool's configuration.

Once you have confirmed that both files are stale Atoms output, move only those
two files into a backup directory:

```bash
mkdir -p .atoms
backup_dir="$(mktemp -d "$PWD/.atoms/stale-wrangler.XXXXXX")"
mv atoms-worker/.wrangler/deploy/config.json \
   atoms-worker/.wrangler/deploy/wrangler.json "$backup_dir/"
```

Keep `atoms-worker/wrangler.jsonc` and `.wrangler/state` in place. The latter
contains local Durable Object data. Do not delete `.wrangler/` to clear a redirect.

Restart the intended environment, for example with `vendor/bin/atoms dev --env
staging`, and check the Worker name in its settings report. Do not run two Atoms
commands against the same Worker directory concurrently.

The interrupted-run report for Atoms 0.9.1 involved a Ctrl+C byte sent to a
non-TTY session. It did not establish that ordinary terminal Ctrl+C leaves stale
files. Report that case separately with the terminal and process details if you
observe it.

## `atoms-composer.json`

`atoms init` also writes this file. It lists the Composer packages that ship
inside the Atom, separate from your application's own `composer.json`:

```json title="atoms-composer.json"
{
    "require": {
        "atoms/database-illuminate": "^0.9"
    }
}
```

The file accepts `require` and `repositories`, and each required package must
be on the [package
allowlist](https://github.com/AtomsPHP/atoms/blob/main/packages/cli/resources/allowed-packages.json).
`atoms build` resolves the file and writes
`atoms-composer.lock` beside it. Commit the lock file so every build installs
the same versions.

## Application settings

Your application needs two settings to call its Atoms:

- `ATOMS_ENDPOINT` is the URL of the deployed Worker: its
  `https://<worker_name>.<subdomain>.workers.dev` URL, or one of its
  [custom domains](/guides/environments/#custom-domains). For a local Worker
  started by `atoms dev`, use `http://127.0.0.1:8787`.
- `ATOMS_SHARED_SECRET` is the same [shared
  secret](/guides/secrets/#the-shared-secret) the Worker holds.

In Laravel, set both in `.env`, and `config/atoms.php` reads them:

```dotenv
ATOMS_ENDPOINT=https://atoms.example.com
ATOMS_SHARED_SECRET=…
```

In Symfony, read them in `config/packages/atoms.yaml`:

```yaml
atoms:
    endpoint: '%env(ATOMS_ENDPOINT)%'
    shared_secret: '%env(ATOMS_SHARED_SECRET)%'
```

In plain PHP, pass `endpoint` and `sharedSecret` to `AtomsConfig::fromArray()`,
as the [plain-PHP
example](https://github.com/AtomsPHP/atoms/tree/main/examples/plain-php) does.

For the optional settings, see the comments in Laravel's published
`config/atoms.php`, or the [Symfony
quickstart](/getting-started/symfony/#configure-atoms). Each environment's
`callback_url` in `atoms.json` should point at your application's callback
route, `/atoms/callback` by default.
